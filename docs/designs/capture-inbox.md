## Problem Statement

Every transaction reaches monai through BudgetBakers Wallet today: the owner types each purchase into the Wallet phone app on the spot, then exports a CSV and imports it. The goal is to delete Wallet entirely and make monai the only ledger, fed by:

- **bank and e-wallet history exports**, weekly or monthly, from several institutions in mixed formats (CSV, XLSX, PDF);
- **receipt photos and short text messages sent from Discord** on the phone;
- **Claude / Codex through the monai MCP server**, which today exposes read tools only;
- **monai chat**, which already proposes writes.

The owner's constraint: "make sure that the UX is the same if we're adding from discord chat, claude/codex, or monai chat."

## What Makes This Cool

- Capture happens wherever you already are: the phone right after paying, a Claude conversation, monai chat. It always produces the same card with the same actions.
- Statements stop being imports. They become a reconciliation diff: "41 cleared, 3 you never logged, 1 possible duplicate, 1 transfer pair."
- LLM-read numbers can't be one-tap approved unless they pass arithmetic invariants printed on the statement itself. The invariants catch most misreads, not all (see premise 3).
- The Discord bot reaches localhost without exposing anything. It makes an outbound connection to Discord's gateway, so monai stays bound to `127.0.0.1`.

## Constraints

- monai binds to `127.0.0.1` only (Phase 30 guard rejects `0.0.0.0`); no public endpoint, no tunnel.
- Correctness by construction: the LLM selects parameterized operations, never emits SQL; agent writes are confirmed, validated, audit-logged proposals.
- Repo is public: tests and fixtures use synthetic rows only; real exports stay local and gitignored (`report_*.csv` precedent).
- Single currency (IDR) for spending.
- Code facts this design must change:
  - `Transaction` (`backend/models.py:130`) has no provenance columns: nothing records where a row came from or whether a statement confirmed it.
  - Proposal TTL is a global 15 minutes (`backend/tools.py:720`, enforced at `backend/main.py:1556`). That's too short for "snap at lunch, approve after dinner" and for weekly batches.
  - `POST /proposals/{id}/confirm` (`backend/main.py:1535`) requires the API key **and** the per-proposal token. The token is returned only to the session that created the proposal and is never serialized by `GET /proposals`. So today only the originating channel can confirm.
  - MCP registers only `READ_TOOL_NAMES` (`backend/mcp_server.py:82`, D-03). It is mounted at `/mcp` behind the same `MONAI_API_KEY` (`backend/main.py:202`), so every MCP client config holds that key.
  - `backend/importer.py` is Wallet-specific and has no dedup.
- Pre-existing limit, not fixed here: the Next.js proxy injects keys into every request (`ui/app/api/[...proxy]/route.ts`), so any process on the host that can reach `127.0.0.1:3001` has full write. A local agent with shell access (e.g. Claude Code) can bypass every approval gate in this design through that proxy. The gates below protect against MCP-only clients (Claude Desktop, Codex without host shell) and remote Discord users, not against a shell-capable agent on the host.

## Premises (agreed)

1. **Capture first, statement clears.** Rows from Discord, Claude/Codex and monai chat are approved into the ledger as **uncleared**. A statement import marks matching rows **cleared**, proposes rows you never logged, and flags likely duplicates. If a match's amounts disagree, the bank's amount wins, but only after you accept that match (see Matching). *(Revised after the second opinion; the original said statements come first and receipts enrich them.)*
2. **Every new channel produces proposals.** Discord, MCP, statement imports and monai chat never write directly. They all use the same `proposals` table, validation and audit log. Existing direct REST writes (UI manual entry, Wallet `POST /import`) stay direct until the Wallet cutover and set `source` like everything else.
3. **Invariants gate LLM output.** An LLM-extracted batch is one-tap approvable only if **all** of these hold: the statement prints opening and closing balances and opening + rows = closing; the row count equals the printed count when one is printed; every row date falls inside the statement period; and every row's running balance matches when the export prints one. A batch with no printed balances is always flagged; there is no fallback to monai's own balance. **Not caught when there's no per-row running balance:** amounts swapped between rows, offsetting misreads, and descriptions attached to the wrong row. The card says which invariants ran ("sum only" vs "running balance verified").
4. **Discord bot is outbound-only.** It runs on the monai host and accepts input (text, photos, button presses) only from the owner's Discord user ID, in DMs only. Other senders are ignored and logged. Accepted trade-off: whoever controls the owner's Discord account can create and approve writes.
5. **MCP can't self-approve.** MCP gains `propose_*` tools, `reject_proposal(id)`, and `confirm_proposal(proposal_id, code)`. The code is displayed only in monai-controlled channels (monai Inbox, Discord). MCP results never contain the proposal token, the code, or the approver key (Decision D2, logged).
6. **Wallet history stays.** Existing rows are backfilled as cleared legacy rows. Statements overlapping them match and skip instead of inserting.
7. **One card everywhere.** The backend renders a single canonical card. Each channel shows it natively: monai chat card, Discord embed + buttons, MCP text result. **Capture cards** are identical in fields and wording across channels. **Batch cards** show the same summary everywhere (counts, invariant status, warnings), with per-row review only in the Inbox. Acting in one channel updates the others. Accepted exception: in MCP, Approve takes a code from a trusted channel (see Approval).

Vocabulary: **pending / confirmed / rejected / expired / superseded / locked** are proposal states. **uncleared / cleared** are transaction states (awaiting / confirmed by a statement, or legacy).

## Mechanics

### Provenance schema (migration, slice 1)
- `transactions`: `source` (`legacy` | `wallet_csv` | `ui` | `chat` | `mcp` | `discord` | `statement` | `adjustment` | `investment`), `cleared_at` (nullable), `external_ref` (nullable), `statement_desc` (nullable text, the bank's own description), `statement_batch_id` (nullable FK to the confirming proposal).
- `proposals`: `channel` (where it was created), `supersedes_id` (nullable), `code_hash` (nullable), `failed_attempts` (int, default 0). New statuses `expired`, `superseded`, `locked`.
- Backfill: every existing transaction gets `source='legacy'` and `cleared_at = migration time`. It only fills new NULL columns, never changes or deletes data. Per the project rule, it still ships with a dry-run mode that prints counts first. After the backfill, `source` is NOT NULL.
- External ref: `sha256(account_id, date, amount, normalized_desc, n)`, where `n` is the occurrence ordinal among identical lines in the same statement. When the export prints a running balance, that replaces `n`. Unique index on `(account_id, external_ref)` where not null. Re-importing the same file reproduces the same refs, and those rows are reported as "already imported", never raised as an IntegrityError.

### Insert paths and their `source` (test: no new row has a NULL or wrong source)
| Path | source |
|---|---|
| `importer.import_csv_text` (Wallet, until cutover) | `wallet_csv` |
| UI `POST /transactions` | `ui` |
| `apply_add_transaction` / `apply_add_transfer` via a proposal | the proposal's `channel` (`chat` / `mcp` / `discord`) |
| balance adjustments | `adjustment` |
| funded buy/sell and investment transfer counter-legs | `investment` |
| `import_batch` inserts | `statement` (born cleared) |

New captures start uncleared. `adjustment`, `investment` and `statement` rows start cleared. Accounts flagged `statement_less` (e.g. Cash) never expect clearing and never appear in Unmatched.

### Matching (`backend/reconcile.py`, pure function)
`match(statement_rows, candidates) -> {matched, already_imported, new, ambiguous, transfers}`

- **Candidates:** every row in the statement's account within the period ± window: uncleared rows (to clear), cleared statement rows and legacy rows (to skip).
- **Matched** (auto-accept): exact amount, date within the window (default ±3 days, set by the Assignment), best fuzzy-description score, a unique best candidate, and the candidate is uncleared.
- **Already imported** (skip): same `external_ref`, or an exact-amount, in-window match against a cleared statement row or legacy row. This covers overlapping weekly and monthly exports and the same period arriving as CSV and as PDF.
- **Ambiguous** (never auto): two or more candidates; amount within tolerance but not exact (`|Δ| ≤ max(1%, 5,000 IDR)`, e.g. a fee folded in); possible many-to-one. The card shows both amounts and offers "accept match (bank amount wins)", "treat as new", or "skip".
- **New:** no candidate.
- **Field precedence on clear:** amount ← statement (only exact matches or accepted ambiguous ones); date ← capture (purchase time; the posting date stays in `statement_desc` context and the audit log); merchant, category, notes ← capture; `statement_desc` ← statement. Every overwrite shows on the card and is audit-logged with before/after.
- **Non-IDR rows** are flagged and the batch loses one-tap approval. They're never summed into an invariant unconverted.
- **Transfers:** a row classified as a transfer looks for its counter-leg in the other account (uncleared or cleared, within the window). Found: clear this leg and link `transfer_pair_id`. Not found: create both legs through `apply_add_transfer`, with the other account's leg uncleared, so that account's statement later clears it instead of inserting. Synthetic tests cover both orderings.

### Batch review and apply
- Each batch row stores a decision in the proposal payload: matched and new default to accept; ambiguous defaults to unresolved. The Inbox edits decisions per row (accept / skip / edit fields) via `PATCH /proposals/{id}/rows` (approver key). Each edit re-runs the invariants.
- A batch can be approved only when no row is unresolved. Skipped rows are recorded in the audit log. There is no other partial apply.
- **Re-validation on approve:** confirm re-runs `reconcile.match` against current ledger state. If the result differs from the stored one (a matched row edited or deleted, a new capture appeared), the approve returns 409 and the proposal is superseded by a fresh one with the new diff. Proposals that reference an existing row (enrichment, supersede) carry the row's `before` snapshot and fail on mismatch the same way.

### Approval (works from any trusted channel)
- New `POST /proposals/{id}/approve` and `/reject`. They require `MONAI_APPROVER_KEY`, a second secret held only by the Next.js server proxy (UI) and the bot, and never placed in any MCP client config. Same checks as confirm: `SELECT … FOR UPDATE`, status must be pending, not expired. The status check under the row lock is the replay protection. The existing token-based `/confirm` stays for the originating chat session.
- **MCP code:** 6 characters from the Crockford base32 alphabet (30 bits). It is generated per proposal at creation and stored as `code_hash`. It is valid only for that `proposal_id`, only until the proposal leaves `pending` (approved, rejected, expired, superseded), single use. After 5 failed attempts on one proposal, the proposal becomes `locked`: still approvable from the Inbox or Discord, never from MCP. After 20 failed attempts across all proposals in an hour, MCP confirm is disabled until the next hour. Tests: missing code, wrong code, attempt cap, lockout, code absent from every MCP tool result.
- **MCP actions:** Approve = `confirm_proposal(id, code)`. Reject = `reject_proposal(id)` (rejecting is always safe, so no code). Edit = ask the assistant to re-propose, which calls `propose_*` with `supersedes=id`. The old proposal becomes `superseded`, and the code is shown again for the new one.

### Cross-channel status
- `GET /proposals?changed_since=<ts>` returns status changes. Expiry is applied lazily: any read past `expires_at` flips a pending proposal to `expired`.
- The bot polls it every 5 seconds (localhost, cheap) and edits its Discord message on any change: "✓ Approved in monai · 10:14", "Expired", "Superseded by a newer proposal". monai chat cards and the Inbox poll the same endpoint while visible. LISTEN/NOTIFY is the upgrade if polling ever shows up in a profile.
- Per-operation TTL replaces the global 15 minutes: chat captures keep 15 minutes; Discord and MCP captures 48 hours; `import_batch` 7 days.

### Inbox tabs
- **Pending:** proposals with status `pending` or `locked`, any channel except batches.
- **Statement batches:** pending `import_batch` proposals, with per-row review.
- **Unmatched:** uncleared transactions older than 14 days in accounts that expect statements.
- **History:** confirmed, rejected, expired and superseded proposals.

### Channel rendering
- `render_card(proposal) -> dict` is the only place card content is decided. Renderers: monai React card, Discord embed, MCP text.
- Batch cards outside the Inbox show summary counts, invariant status, warnings and an Inbox link. Discord offers "Approve N matched" only when the batch is one-tap approvable with zero unresolved rows; otherwise "Review in monai".
- Snapshot tests cover each renderer's output for one capture card and one batch card.

### Receipts
- Extract merchant, amount, date and a category guess (no line items, since nothing would consume them).
- Run `reconcile.match` against uncleared rows. A unique match yields an `enrich_transaction` proposal, which may change merchant, category and notes only, never amount or date. Anything else yields a new capture proposal.

## Recommended Approach

**Approach B, shipped in slices. Each slice is usable on its own.** Mechanics above define the details.

**Slice 1: Reconcile core + minimal Inbox** (no new services)
- Provenance migration with dry-run backfill; `source` set on every insert path.
- `backend/reconcile.py` + `test_reconcile.py` (synthetic rows: exact, near-amount, identical lines, overlapping re-import, cross-format re-import, both transfer orderings).
- `backend/parsers/` with one deterministic parser for the highest-volume account, plus the invariants.
- `import_batch` operation with per-row decisions and re-validation on approve; per-operation TTL; lazy expiry.
- `POST /import/statement`; approver key + `/approve` / `/reject`; `PATCH /proposals/{id}/rows`.
- Minimal `/inbox` page: Pending and Statement batches tabs, per-row batch review, MCP codes displayed on pending MCP cards.
- MCP: `propose_add_transaction`, `reject_proposal`, `confirm_proposal(id, code)` with the attempt cap.

**Slice 2: One card, three channels**
- `render_card` + per-renderer snapshot tests; the monai chat card and Inbox move onto it.
- `bot` service in docker-compose (`discord.py`, outbound gateway, host network like `backend`). It accepts only owner DMs. Text capture ("kopi 35k gopay") goes through the existing agent with propose-only tools, then the bot posts the card with buttons that call `/approve` / `/reject` with the approver key. Edit opens a Discord modal limited to amount, account, category, merchant and date, producing a superseding proposal. MCP codes are also sent as a DM.
- `changed_since` polling for cross-channel status; Unmatched and History tabs.

**Slice 3: Any file, any receipt**
- LLM extraction (configured LlamaIndex provider, vision-capable model) for statement files with no deterministic parser, behind premise 3's invariants.
- Receipt photos via Discord: `enrich_transaction` or a new capture.

**Slice 4: Wallet cutover**
- Import the latest Wallet export and the overlapping statement once. Confirm the duplicate check (Success Criteria) returns zero, then stop using Wallet. `wallet_csv` and the direct import path can then be retired.

**Slice 5 (stretch): Notification forwarding** into the Discord bot as uncleared captures.

Wireframe: `~/.gstack/projects/nikkopg-monai/designs/sketch-20261004/sketch.png` (source `sketch.html` alongside). Shows the same capture card in monai chat, Discord and Claude, the Inbox, a passing statement batch, and a flagged LLM-extracted batch.

## Success Criteria

- Wallet app uninstalled, and a full calendar month recorded entirely through the new channels.
- A monthly statement import for the main account takes under 5 minutes, from export to approved batch.
- **Zero duplicates after cutover:** a committed read-only check (`backend/checks/duplicates.py`) runs `reconcile.match` pairwise within each account, over rows where at least one is not statement-sourced, and returns zero pairs that would auto-match.
- Capture cards render identically in monai chat, Discord and MCP; batch cards render the same summary. Verified by per-renderer snapshot tests.
- No MCP tool can apply a write without a code from a trusted channel. Tests cover missing and wrong codes, the attempt cap and lockout, code/token/key absence from MCP results, and the absence of any MCP tool that applies a write unconditionally.
- An LLM-extracted batch failing any premise-3 invariant cannot be one-tap approved.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R2-1 — feasibility

**Problem**

> Matching lists the candidates as 'uncleared rows (to clear), cleared statement rows and legacy rows (to skip)'. A capture (source chat/mcp/discord/ui) that an earlier statement already cleared is none of these. Matched requires an uncleared candidate, and Already imported names only cleared statement rows and legacy rows. When the next overlapping export arrives (weekly then monthly, or the same period as CSV then PDF, where external_ref differs), every previously cleared capture either lands in 'new' and is inserted again, or has undefined behavior. These are exactly the duplicates the design exists to prevent.

**Remedy**

> Make the candidate set every row in the account within the window, with cleared rows of any source used for skip matching. State that Already imported matches against any cleared row, not only statement-sourced or legacy rows, and add a synthetic test: capture, clear with a weekly export, then re-import an overlapping monthly export in another format.

### R2-2 — feasibility

**Problem**

> match() does not say that each candidate can be consumed by at most one statement row, or which rule wins when a row has both an uncleared and a cleared exact-amount candidate. Without one-to-one assignment, two legitimate 35,000 lines on the same day can both 'match' one legacy or cleared row and both be skipped as already imported, silently losing a real transaction. The skip path is automatic and is never reviewed.

**Remedy**

> Specify one-to-one assignment (each ledger row pairs with at most one statement row, globally, for example by greedy best score or bipartite matching) and the precedence between Matched, Already imported and Ambiguous when candidates of both states exist. Cover this in test_reconcile.py with two identical statement lines against one existing row.

### R2-3 — completeness

**Problem**

> Field precedence on clear sets amount and statement_desc, but does not say whether a cleared capture gets external_ref and statement_batch_id, or where the posting date is kept ('stays in statement_desc context and the audit log' names no column). Without external_ref on cleared captures, the 'same external_ref' skip rule never fires for them and re-import depends entirely on the fuzzy fallback. Without a stored posting date, the posting-date lag the Assignment measures cannot be queried later.

**Remedy**

> State that clearing writes the statement line's external_ref, statement_batch_id and posting date (add a column, or a defined key in the audit 'after'), and that the skip rule checks the external_ref of cleared captures.

### R2-4 — clarity

**Problem**

> The duplicate check runs reconcile.match pairwise 'over rows where at least one is not statement-sourced'. Legitimate identical same-day rows, such as two captured coffees or the many such pairs in legacy Wallet history (both non-statement), still count as auto-matching pairs. The 'zero pairs' success criterion is then unreachable, or gets met by loosening the check. R1-23's false-positive problem remains.

**Remedy**

> Exclude pairs that are backed by distinct statement lines (distinct external_ref or posting identity), and either limit the check to rows created after the cutover or whitelist legacy pairs as a baseline. Define what 'would auto-match' means when neither row is a statement row.

### R2-5 — clarity

**Problem**

> Premise 3's 'opening + rows = closing' does not say which rows are summed. A batch skips already-imported rows and user-skipped rows. If the invariant sums only the rows being applied, every overlapping re-import fails it. 'Each edit re-runs the invariants' also leaves open whether an Inbox amount edit changes the summed value, which would let a hand edit turn a failing LLM batch into a passing one.

**Remedy**

> State that the invariants run over every parsed statement row, including already-imported and skipped rows, using extracted amounts. Say whether a row edit changes the extracted value checked by the invariant, and how an edited row is marked on the card.

### R2-6 — clarity

**Problem**

> Premise 3 and the success criterion gate only LLM-extracted batches. They don't say whether a deterministic-parser batch (slice 1's only path) needs printed balances or any invariant before Discord's one-tap 'Approve', or what its card says about checks run. A deterministic parser can misparse after a format change just as silently.

**Remedy**

> State whether deterministic batches run the same invariants and the same one-tap gate (recommended), or document the exemption and why it is safe.

### R2-7 — completeness

**Problem**

> Re-validation on approve supersedes the batch with 'a fresh one with the new diff' whenever the match result changes, including when 'a new capture appeared'. With daily Discord captures landing inside the period ± window, a batch reviewed over a 7-day TTL can be superseded during or after review. Nothing says the owner's per-row decisions (accepted ambiguous matches, skips, field edits) carry over, so review work is lost and the owner must redo it.

**Remedy**

> Specify that decisions for statement rows whose match is unchanged carry into the superseding proposal (keyed by external_ref), and that only changed rows reset to unresolved. Show the changed rows on the card.

### R2-8 — feasibility

**Problem**

> The transfer rule starts from 'a row classified as a transfer' and 'its counter-leg in the other account', but never says how a statement row is classified as a transfer or how the other account is determined from a bank description (for example, a top-up to an e-wallet). It also leaves the case where the counter-leg exists but this account's leg does not (for example, the counter-leg was captured as one-sided income): 'clear this leg' has nothing to clear.

**Remedy**

> Define transfer classification (a per-account description rule, an owner-maintained mapping, or an always-ambiguous fallback offering 'pair with account X') and target-account resolution. Define behavior when only the counter-leg exists: insert this leg cleared and link it, or flag as ambiguous.

### R2-9 — consistency

**Problem**

> The insert-path table is incomplete in three ways. Proposal channel values cover chat, mcp and discord, but a statement upload creates an import_batch proposal whose channel is unnamed. 'import_batch inserts are statement (born cleared)' conflicts with the transfer rule that creates the other account's leg uncleared through apply_add_transfer, whose own table row says source is the proposal's channel. And the initial cleared state of wallet_csv and ui rows ('New captures start uncleared') is implied, not stated.

**Remedy**

> Enumerate proposals.channel values (including the statement upload's). Give import_batch's transfer counter-leg an explicit source and cleared state. State whether wallet_csv and ui rows start uncleared.

### R2-10 — completeness

**Problem**

> Mechanics rely on accounts flagged statement_less (Cash never appears in Unmatched), but the provenance migration lists only transactions and proposals columns. The Account model has no such column, and nothing says who sets the flag, what its default is, or whether existing accounts are backfilled.

**Remedy**

> Add accounts.statement_less (boolean, its default, and the backfill for existing accounts) to the slice 1 migration and name the UI or setting that toggles it.

### R2-11 — completeness

**Problem**

> Receipts run reconcile.match 'against uncleared rows' only, and anything else yields a new capture. A receipt photographed after its text capture was cleared by a statement, or for a purchase that entered as a statement 'new' row, creates a duplicate uncleared capture. No later statement will clear it (its period has passed), so it sits in Unmatched and breaks the zero-duplicates criterion.

**Remedy**

> Match receipts against cleared and uncleared rows, so enrich_transaction (merchant, category and notes only) can target a cleared row. Create a new capture only when no candidate exists, and make an ambiguous result offer 'enrich X' or 'new'.

### R2-12 — completeness

**Problem**

> The Wallet transition has no dedup story. The importer 'has no dedup' (Constraints) and stays live through slices 1 to 3, while slice 2 starts Discord capture, so the same purchase can enter as both wallet_csv and discord. Slice 4's 'Import the latest Wallet export' will duplicate legacy rows if that export overlaps the backfill, and wallet_csv rows don't pass through reconcile.

**Remedy**

> Specify the transition rule: Wallet imports after the migration must start after the backfill timestamp (or route through reconcile as a batch), and either Discord capture and Wallet typing don't overlap or wallet_csv rows are matched against captures. State the cutover import's date bounds.

### R2-13 — completeness

**Problem**

> A proposal locked after 5 failed MCP code attempts can be superseded from MCP ('Edit = re-propose ... supersedes=id'), which creates a fresh proposal with a new code and failed_attempts back at 0. This defeats the per-proposal lockout. Only the global 20-per-hour cap remains.

**Remedy**

> Forbid MCP from superseding a locked proposal, or carry failed_attempts and the locked state into the superseding proposal. Add this case to the lockout tests.

### R2-14 — clarity

**Problem**

> 'Rejecting is always safe, so no code' is not true for every proposal. reject_proposal(id) and supersedes=id are not scoped to MCP-created proposals, so an MCP agent (possibly prompt-injected through tool output) can reject or supersede an import_batch carrying days of per-row review, or a Discord capture before the owner sees it.

**Remedy**

> Restrict MCP reject and supersede to proposals created by MCP (or to capture operations), and exclude import_batch. Otherwise state the accepted risk explicitly.

### R2-15 — completeness

**Problem**

> Lazy expiry 'flips a pending proposal to expired', but locked proposals (still approvable from the Inbox or Discord) are not covered. They never expire, stay in the Pending tab indefinitely, and remain approvable long after their TTL.

**Remedy**

> Apply expiry to both pending and locked proposals, and have approve, the Inbox and Discord treat an expired locked proposal like any expired one.

### R2-16 — completeness

**Problem**

> GET /proposals?changed_since=<ts> needs a per-proposal status-change timestamp, but the proposals table has only created_at and confirmed_at, and the migration adds none. Lazy expiry also only fires on 'a read' of a proposal. A changed_since query that filters by change time never selects a proposal whose expires_at passed silently, so the bot never sees 'Expired'.

**Remedy**

> Add proposals.status_changed_at (set on every transition, including lazy expiry and supersede) to the slice 1 or 2 migration. Make the changed_since handler apply expiry to all pending and locked proposals past expires_at before filtering.

### R2-17 — clarity

**Problem**

> Ambiguous lists 'possible many-to-one', yet its only actions are 'accept match (bank amount wins)', 'treat as new' and 'skip'. Accepting a many-to-one match has no defined meaning: which captures clear, whether amounts are split or overwritten, and whether some captures get deleted. The Assignment decides whether many-to-one is needed, but the committed card already offers the action.

**Remedy**

> Until the Assignment decides, offer only 'treat as new' and 'skip' for many-to-one rows. Otherwise define accept semantics (clear all N captures and their sum check, with no overwrite).

### R2-18 — clarity

**Problem**

> Discord's one-tap button reads 'Approve N matched', but approving the batch also inserts every 'new' row (new rows default to accept). The label understates what the tap writes. That conflicts with the core value of never changing data without the owner's informed say-so.

**Remedy**

> Label the button with every effect, for example 'Approve: N clear, M new, K skip', or show only 'Review in monai' when the batch contains new rows.

### R2-19 — completeness

**Problem**

> The Unmatched tab lists uncleared transactions older than 14 days, but defines no action for them. A capture booked to the wrong account, a cash payment, or a purchase the bank never posted has no resolution path (move account, mark cleared manually, delete via proposal, or dismiss), so the tab grows without bound.

**Remedy**

> Define the actions per Unmatched row and say whether each goes through a proposal (for example, edit account, mark cleared with a reason, delete).

### R2-20 — completeness

**Problem**

> Non-IDR rows are flagged and cost the batch its one-tap approval, but the batch review model does not say what 'accept' does for such a row (insert in the foreign currency, which breaks the IDR constraint, or require an IDR amount). Indonesian statements often print the settled IDR amount next to the original currency, which changes the answer.

**Remedy**

> State that a non-IDR row cannot be accepted until it carries an IDR amount (the statement's settled IDR value, or a manual edit), or that it can only be skipped.

### R2-21 — feasibility

**Problem**

> The backfill 'ships with a dry-run mode that prints counts first' and then sets source NOT NULL. Per project memory, entrypoint.sh runs alembic upgrade head on every container start, and the document says neither how dry-run is invoked under automatic upgrade nor what happens to the NOT NULL step if dry-run is the default. If it is the default, columns stay NULL and the constraint fails. If it isn't, the dry-run never runs before the real change.

**Remedy**

> Either drop the dry-run for this purely additive fill and say so, or define the arming mechanism (an env flag, with dry-run as the default) and split NOT NULL into a later revision that runs only after an armed backfill.
