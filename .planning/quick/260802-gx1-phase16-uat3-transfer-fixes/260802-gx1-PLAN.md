# Quick Task 260802-gx1: Fix Phase 16 UAT #3 transfer bugs

## Problem

Phase 16 UAT #3 (live liquid↔liquid Transfer against real Postgres) ran and
surfaced two real defects, both traceable to `is_transfer=true` being treated
as "ignore for balance":

1. **Balances never moved after a transfer.** `tools.py:account_balances`
   excluded `is_transfer` rows from `current_balance`
   (`LEFT JOIN transactions t ... AND t.is_transfer = false`). A transfer's two
   legs are both `is_transfer=true`, so neither the source debit nor the
   destination credit ever reached any account's derived balance — the liquid
   account card and total liquid balance were unchanged. Same bug silently
   hid balance-adjustment rows (also `is_transfer=true`) from the card and
   overstated net worth after any liquid→investment funding transfer (the
   liquid side never dropped). The `apply_add_balance_adjustment` docstring
   already flagged this as "Finding 2".

2. **Deleting a transfer leg 500'd.** The REST `DELETE /transactions/{id}`
   endpoint and the agent proposal path both called the D-04-guarded
   `apply_delete_transaction` without pair handling. A transfer leg has
   `transfer_pair_id` set, so the guard raised `ValueError` — uncaught in the
   endpoint → 500. The guard's own error message pointed at a "pair-aware
   transfer function" that had never been built for delete.

## Tasks

### Task 1 — current_balance must include transfers
- **File:** `backend/tools.py` (`account_balances`)
- **Action:** Drop `AND t.is_transfer = false` from the JOIN so `current_balance`
  sums ALL of an account's transactions (transfers included — a transfer moves
  real money). Keep the transfer exclusion only inside the `period_net` FILTER
  (`FILTER (WHERE t.is_transfer = false ...)`) — cashflow/net-income semantics.
- **Verify:** `test_apply_add_transfer_pairs_both_legs`,
  `test_apply_add_balance_adjustment_delta`, `test_cashflow_summary` pass.
- **Done:** After a liquid↔liquid transfer, source balance drops, destination
  rises, total liquid unchanged; balance adjustments show on the card.

### Task 2 — pair-aware transfer delete
- **File:** `backend/writes.py` (new `apply_delete_transaction_or_pair` +
  `_transaction_snapshot` helper); `backend/main.py` (route both delete call
  sites through the wrapper + import it).
- **Action:** New wrapper deletes BOTH legs of a transfer (looks up all rows
  sharing `transfer_pair_id`, calls the primitive with `allow_paired=True`,
  audits each). A half-transfer would leave money unconserved. The D-04
  guard/primitive and its test are left intact — this is the pair-aware
  composition the guard's message referenced.
- **Verify:** `test_paired_leg_delete_blocked` (guard still works) and new
  `test_delete_transaction_or_pair_removes_both_legs` pass.
- **Done:** Deleting either leg from the recent-transactions list removes both
  legs with no 500 and no orphan.

## Out of scope (deferred)

The cash leg of a liquid→**investment** funding transfer has
`transfer_pair_id=None` (it links to its PortfolioEvent via
`source_account_id`, not a pair id), so deleting it won't cascade to the event.
Tracked as a separate follow-up (block-vs-cascade decision needed).

## must_haves

- **truths:**
  - A liquid↔liquid transfer moves both account balances; total liquid is unchanged.
  - Deleting one leg of a transfer deletes both legs (REST + agent paths).
  - The single-leg D-04 delete guard still raises for a bare primitive call.
- **artifacts:** `backend/tools.py`, `backend/writes.py`, `backend/main.py`,
  `backend/tests/test_write_tools.py`
- **key_links:** `account_balances` (tools.py), `apply_delete_transaction_or_pair`
  (writes.py), `delete_transaction` + `_execute_proposal_payload` (main.py)
