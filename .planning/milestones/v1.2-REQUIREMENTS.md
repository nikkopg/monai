# Requirements: monai v1.2 — Connected Ledger (Liquids ↔ Investments)

**Defined:** 2026-07-18
**Core Value:** You can understand and manage your entire financial life — spending and investments — by talking to a trustworthy AI that never fabricates a number and never changes your data without your say-so.

**Reference:** BudgetBakers Wallet web app (dashboard, Records tab, Add-record modal, Settings > Categories) — captured live 2026-07-18. Deliberately trimmed: templates, payer, payment type/status.

## v1.2 Requirements

Requirements for this milestone. Each maps to roadmap phases.

### Dashboard (NW)

- [x] **NW-01**: User sees a main dashboard where net worth = liquid accounts + investment platforms, each counted exactly once
  - *Outcome: validated.* Shipped Phase 15 as a composed `net_worth` read tool with an asserted 100%-coverage account-type filter, surfaced as the `/cashflow` hero.
- [x] **NW-02**: User sees the liquid vs investment split with per-side breakdowns on the dashboard
  - *Outcome: validated.* Shipped Phase 15 alongside NW-01, same endpoint/hero.

### Accounts (ACCT)

- [x] **ACCT-01**: User can add, edit, and remove liquid accounts in a dedicated account manager
  - *Outcome: validated.* Shipped Phase 16 (`AccountManager.tsx` create/edit/delete with `type: liquid`).
- [x] **ACCT-02**: User can set an account's balance; the delta is stored as a visible "Adjustment" record (balances stay derived, never a stored field)
  - *Outcome: validated.* Backend write primitive shipped Phase 13; UI entry point (row action + delta-preview modal) shipped Phase 18.
- [x] **ACCT-03**: Accounts are typed liquid/investment (DB-enforced after live audit + backfill); investment-typed accounts are excluded from cashflow totals — the double-count fix
  - *Outcome: validated.* Shipped Phase 12 — CHECK constraint + `cashflow_transactions` view exclusion, all 10 cashflow-total call sites switched.

### Records (REC)

- [x] **REC-01**: User can browse all records in a date-grouped ledger with a daily net per group
  - *Outcome: validated.* Shipped Phase 17 (Records tab).
- [x] **REC-02**: User can filter records by search, account, category, record type, amount range, and transfer visibility
  - *Outcome: validated.* Shipped Phase 17.
- [x] **REC-03**: User can select multiple records and bulk delete or bulk recategorize
  - *Outcome: validated.* Shipped Phase 17 (bulk endpoints + UI multi-select).
- [x] **REC-04**: User can add a record via a modal with Expense / Income / Transfer segmented form (amount + currency, account, category picker, date-time, note; "add another")
  - *Outcome: validated.* Shipped Phase 16 (`TransactionModal.tsx` extension).
- [x] **REC-05**: Transfer pairs display as one logical unit; editing or deleting affects both legs atomically (single-leg edits blocked)
  - *Outcome: validated.* Shipped Phase 17, backed by Phase 13's pair-aware guard.

### Categories (CAT)

- [x] **CAT-01**: Categories are first-class entities (name, color, icon, parent) with up to 3 hierarchy levels
  - *Outcome: validated.* Shipped Phase 11.
- [x] **CAT-02**: User can manage categories in Settings — add, edit, delete with a block-or-reassign guard (no orphaned records)
  - *Outcome: validated.* Shipped Phase 11 (Settings tree manager, moved from Cashflow).
- [x] **CAT-03**: The 74 existing category strings migrate onto the hierarchy via a human-reviewed mapping with row/sum parity checks; destructive column drop is a separate later migration
  - *Outcome: validated.* Shipped Phase 11 — migration 009 + human-reviewed CSV, parity + idempotency proven; free-string column intentionally left in place (drop deferred, not scheduled).
- [x] **CAT-04**: Record forms, filters, and dashboard charts use the hierarchical category picker
  - *Outcome: validated.* Shipped Phase 11.

### Platforms (PLAT)

- [x] **PLAT-01**: User can open a platform detail view with a PnL tab and a buy/sell history tab
  - *Outcome: validated.* Shipped Phase 17.
- [x] **PLAT-02**: Platform manager reaches CRUD parity with the account manager (extends existing `PlatformManager.tsx`)
  - *Outcome: validated.* Shipped Phase 16.

### Connection layer (XFER)

- [x] **XFER-01**: User can transfer between liquid accounts; stored as paired records via `transfer_pair_id`
  - *Outcome: validated.* Shipped Phase 13 (`apply_add_transfer`).
- [x] **XFER-02**: User can transfer liquid → investment platform (transaction linked to a portfolio deposit event via `source_account_id`)
  - *Outcome: validated.* Backend shipped Phase 13; UI entry point ("Deposit cash" on platform detail) shipped Phase 18.
- [x] **XFER-03**: Buy/sell requires choosing a liquid source/destination account; one confirmation writes both entries in one DB transaction
  - *Outcome: validated, with a data-loss bug found and fixed during UI close-out.* Backend shipped Phase 13; UI entry point (HoldingModal funding selector) shipped Phase 18. Live UAT surfaced `recompute_holding_from_events` silently clobbering legacy holdings with no backing `portfolio_events` rows — fixed via Alembic migration 012 (opening-event backfill, parity-asserted) plus a write-path guard. See memory `recompute-clobbers-eventless-holdings`.
- [x] **XFER-04**: Cross-currency entry uses dual amounts (sent + received, each with currency); USD assets valued in IDR via existing FX cache
  - *Outcome: validated.* Shipped Phase 13.
- [x] **XFER-05**: Historical imported transfer rows are retro-paired by migration (matched by date+amount; unmatched flagged, left as-is)
  - *Outcome: validated.* Shipped Phase 13 (migration 011).

### Chat (CHAT — continues v1.0 numbering)

- [x] **CHAT-09**: User can perform the new operations (records, transfers, funded buy/sell, category changes) via chat with the existing confirm-before-write flow; new write tools registered on the agent and kept off the MCP read-only surface
  - *Outcome: validated.* Shipped Phase 14 — 5 new `propose_*` tools dual-registered, dispatched via existing confirm flow, kept out of `READ_TOOL_NAMES`.

## Deferred / Emerged During Milestone

- **Net-worth-over-time (historical net worth on the trend chart)** — not an original v1.2 requirement, but attempted mid-Phase-18 close-out as a natural extension of NW-01/NW-02. Found unreconstructable from monai's current ledger: the original Wallet CSV import silently dropped an entire "Investements" account and its BCA→Investements transfer legs, causing liquid balances to drift (BCA read ~150M too high for months); investment-side history is also shallow (`portfolio_value_history` only began 2026-07-11). Built, found dishonest, reverted (commit `bc4c02c`). **Deferred to the next milestone** as a reconstruction effort sourced from the original Wallet export. See memory `networth-history-needs-adjustment-anchor` and `.planning/PROJECT.md` Next Milestone Goals.

## Out of Scope

Explicitly excluded. Documented to prevent scope creep.

| Feature | Reason |
|---------|--------|
| Record templates (Wallet feature) | Single-user YAGNI; "add and create another" covers repeat entry |
| Payer / payment type / payment status fields | Single-user YAGNI; note field suffices |
| Forced live-FX on cross-currency entry | Violates never-fabricate principle; manual dual-amount is authoritative (Firefly III "foreign amount" pattern) |
| Investment cash as an `accounts` row | Would reintroduce double-counting; investment cash lives in platforms/holdings |
| Free-form SQL from agent | Standing exclusion — confident-wrong-number risk |
| Write tools over MCP to external clients | Standing exclusion — writes stay in the web app |
| Multi-currency for *spending* records | IDR-only holds (0/5608 skipped); currency fields on records exist for transfer legs only |
