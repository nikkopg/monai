# Roadmap Archive: v1.2 — Connected Ledger — Liquids ↔ Investments

**Archived:** 2026-09-05
**Status:** SHIPPED
**Phases:** 11-18 (8 phases, 31 plans)

For the current roadmap, see `.planning/ROADMAP.md`.

---

**Milestone Goal:** Restructure monai around a single trustworthy net worth: liquids and
investments as two connected subsystems that never double-count, linked by real
transfer/buy-sell mechanics, with BudgetBakers-grade record and category management.

## Key Accomplishments

1. **Categories became first-class, hierarchical entities.** All 74 free-string category
   values were migrated onto a 3-level (name/color/icon/parent) hierarchy via a
   human-reviewed mapping with row/sum parity checks — zero data loss, zero silent
   recategorization. Record forms, filters, and dashboard charts all read from the
   hierarchy, not the old free-string column. (Phase 11)
2. **`accounts.type` became a real, DB-enforced discriminator.** All 4 live accounts were
   manually audited and classified liquid/investment, the column got a CHECK constraint,
   and every cashflow total was switched to a `cashflow_transactions` view that excludes
   investment-typed accounts by construction — the investment double-count bug is now
   structurally impossible, not just avoided by convention. (Phase 12)
3. **One shared, atomic mutation layer covers every new kind of money movement.**
   `writes.py` gained `apply_add_transfer`, `apply_add_investment_transfer`,
   `apply_add_funded_buy/_sell`, and `apply_add_balance_adjustment` — each writing every
   affected row (paired transaction legs, portfolio events, holdings) in one DB
   transaction, with account balances staying derived rather than stored. (Phase 13)
4. **Every new write is reachable from REST, agentic chat, and correctly excluded from
   the external MCP surface.** Five new operations got dual-registered propose/confirm
   agent tools and direct REST endpoints, both routed through Phase 13's `apply_*`
   functions — with `READ_TOOL_NAMES` iterated (not re-typed) to keep writes off the
   MCP read-only surface exposed to external clients. (Phase 14)
5. **The dashboard shows one trustworthy net-worth number, split by side.** A composed
   `net_worth` read tool sums liquid account balances + investment platform values with
   an asserted 100%-coverage account-type filter, surfaced as a dashboard hero with a
   liquid/investment breakdown beneath it. (Phase 15)
6. **The UI grew full entry points for the new money-movement primitives.** Account and
   platform managers reached CRUD parity; the record modal grew an Expense/Income/Transfer
   segmented form; a new Records tab shipped a date-grouped, filterable, bulk-actionable
   ledger with atomic transfer-pair editing; platform detail pages got PnL and buy/sell
   history tabs; and Phase 18 wired up the last three user-facing triggers — balance
   adjustment, liquid→investment transfer, and funded buy/sell — directly against the
   Phase 13 write primitives. (Phases 16, 17, 18)

## Notable Findings (Phase 18 close-out)

- **`recompute_holding_from_events` clobbered legacy holdings with no backing events.**
  A funded buy against a holding created before the event-sourcing model (no
  `portfolio_events` rows) made the recompute rebuild the position from just the new
  event, wiping the prior quantity — live UAT #3 destroyed 1691.9681 units of Danamas
  Pasti. Root cause fixed via Alembic migration 012 (backfills opening buy events for
  all 11 event-less holdings, parity-asserted per row) plus a write-path guard so a
  non-zero, event-less holding can never be silently overwritten again. See memory
  `recompute-clobbers-eventless-holdings`.
- **Historical net worth is not reconstructable from monai's current ledger.** An
  attempt to add a net-worth line to the cashflow trend chart surfaced that liquid
  balances drift over time (BCA read ~150M too high for months) because the original
  Wallet CSV import silently dropped an entire "Investements" account and its
  BCA→Investements transfer legs — money that moved to investments still shows as
  sitting in BCA. The line was built, found dishonest, and reverted (commit
  `bc4c02c`); a proper reconstruction sourced from the original Wallet export (which
  does have the dropped account and transfers) was deferred to a follow-up milestone.
  See memory `networth-history-needs-adjustment-anchor`.

### Phase 13: Shared Mutation Layer — Transfer, Buy/Sell-with-Funding, Adjustment Writes

**Goal**: Every new kind of money movement (transfer, funded buy/sell, balance adjustment, category edit) can be written atomically through one trusted layer
**Depends on**: Phase 12 (needs `transfer_pair_id`, `source_account_id`, constrained `accounts.type`)
**Requirements**: ACCT-02, XFER-01, XFER-02, XFER-03, XFER-04, XFER-05
**Success Criteria** (what must be TRUE):

  1. A liquid→liquid transfer writes two paired transaction rows (via `transfer_pair_id`) in one DB transaction; editing or deleting one leg is blocked outside pair-aware functions
  2. A liquid→investment transfer writes a transaction row linked to a portfolio deposit event (via `source_account_id`) in one DB transaction
  3. A funded buy/sell writes the cash-leg transaction and the holding/portfolio-event update together, in one confirmation and one commit — never as two round trips
  4. Setting an account's balance produces a visible "Adjustment" record reflecting the delta; the account balance itself stays derived, never stored
  5. Cross-currency transfer/buy-sell entries accept dual amounts (sent + received, each with its own currency); no write path forces a live-only FX rate
  6. Historical imported transfer rows are retro-paired by a migration pass (matched by date+amount); unmatched rows are flagged and left as-is, not guessed
