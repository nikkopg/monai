<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Next.js proxy | Untrusted form input (from_account, amount) crosses here; the proxy injects MONAI_API_KEY server-side |
| Next.js proxy → FastAPI | `require_api_key`-gated write; FastAPI resolves the account by name and writes the atomic dual-leg transfer |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-18-02-T | Tampering (data integrity) | `from_account` name resolution via `_get_or_create_account` | medium | mitigate | The "From account" field is a `<select>` populated exclusively from a fresh `GET /accounts` fetch and client-filtered to `type === "liquid"`; it submits the exact existing account name. No free-text account input — a mismatching name would silently fork a duplicate account (RESEARCH Pitfall 2). The e2e asserts the field is a `<select>`. |
| T-18-02-I | Information Disclosure | API key exposure | low | mitigate | Submit only through the `/api/...` Next.js proxy (injects MONAI_API_KEY server-side). Never reference `MONAI_API_KEY`, a `NEXT_PUBLIC_` var, or the raw backend URL from the client component. |
| T-18-02-C | Tampering | Client-side amount coercion / preview | low | accept | Server-side Pydantic `gt=0` on `amount` is authoritative; the preview is presentation-only. Client `parseFloat` + `required` are UX/defense-in-depth, not the security boundary. |
| T-18-02-E | Elevation of Privilege | Write reachable off the web app | low | mitigate | investment-transfer stays a web-app-only, API-key-gated REST write; this plan adds no agent/MCP tool and does not touch `READ_TOOL_NAMES` (stays 15). |

No package installs occur in this plan — T-18-SC (supply-chain) is not applicable. No high-severity threats identified.
</threat_model>
