# Phase 16 — UI Design Contract

> Visual and interaction contract for extending `TransactionModal.tsx`, `AccountManager.tsx`, and `PlatformManager.tsx`. This is an EXTEND phase — the design system below is the project's existing locked system (v1.1 "paper" aesthetic), reused verbatim, not proposed. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

| Property | Value |

## Color

Reuses `tokens.color` exclusively — no new hex values introduced.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `tokens.color.card` `#fff` | Modal card background, manager `card` background |
| Secondary (30%) | `tokens.color.sidebar` `#f2efe8` | Segmented-control track background (matches settings) |
| Accent (10%) | `tokens.color.green` `#2f6f4f` | Primary "Save" / "Save & add another" / "Add account" / "Add platform" buttons (`btn` token) only |
| Destructive | `tokens.color.terracotta` `#b5503f` | Delete action links, `dangerBtn`, delete-confirm copy — unchanged from existing managers |
| Active segment | `#fff` bg, `tokens.color.ink` `#23201b` text, `0 1px 2px rgba(40,34,24,.12)` shadow | Selected segment in the 3-way control — verbatim from UIR-07 |
| Inactive segment | `transparent` bg, `tokens.color.muted` `#8b8474` text | Unselected segments |
| Disabled segment (edit-mode transfer lock) | same inactive styling + `opacity: 0.5`, `cursor: "default"` | Locked segmented control when editing an existing transfer leg (see Interaction States) |
| Muted helper/meta text | `tokens.color.muted` `#8b8474` | "Cancel" links, platform `kind` tag, empty-state copy — unchanged |
| Overlay | `rgba(15,17,21,0.72)` | Modal backdrop — unchanged, do not modify |

Accent reserved for: the single primary submit button per form state (Save / Save & add another / Add account / Add platform / Save account / Save platform). Never apply green to the segmented control's active state (that uses ink-on-white per the settings precedent, not green) — this is an intentional, existing distinction between "selection" (ink) and "commit action" (green) already present in the codebase; Phase 16 must not blur it.

No second semantic color is introduced. Destructive stays scoped to delete-related UI exactly as today.

## Component Contracts (Phase 16 specifics)

### 1. Record-type segmented control (REC-04)

Copy the settings-page (`ui/app/settings/page.tsx` L227–264, UIR-07) markup verbatim, swapping the option array and click handler. Exact spec:

- Container: `display: inline-flex`, `background: tokens.color.sidebar`, `border: 1px solid tokens.color.border2`, `borderRadius: 12`, `padding: 4`, `marginBottom: 18`. Placed as the **first element inside the `<form>`**, above the existing 2-col field grid, full width of its own row (the grid starts below it).
- Options, in fixed order: `["expense", "income", "transfer"] as const`. Rendered label: `"Expense"`, `"Income"`, `"Transfer"` (capitalize the value for display; keep the state value lowercase).
- Each segment: `<button type="button">`, `border: none`, `borderRadius: 9`, `padding: "8px 18px"`, `fontSize: 14`.
  - Active: `fontWeight: 600`, `color: tokens.color.ink`, `background: "#fff"`, `boxShadow: "0 1px 2px rgba(40,34,24,.12)"`.
  - Inactive: `fontWeight: 500`, `color: tokens.color.muted`, `background: "transparent"`, `boxShadow: "none"`.
  - `transition: "all .2s ease"` on every segment — matches settings.
- Default active segment on create: **Expense** (D-01).
- **`TransactionModal.tsx` must add `tokens` to its import line** (`import { tokens, card, input, btn, label } from "../styles";`) — it currently only imports `card, input, btn, label`. This is a hard prerequisite, not optional.
- Disabled state (edit mode, existing transfer leg — see Interaction States below): render with `opacity: 0.5`, `cursor: "default"`, and no `onClick` handler on any segment.

### 2. Per-segment field layout (2-col grid, unchanged grid shell)

The existing grid (`display: grid`, `gridTemplateColumns: "1fr 1fr"`, `gap: 10`, `marginBottom: 10`) is reused unchanged. Field order within the grid, top-to-bottom, left-to-right per segment:

**Expense / Income** (6 grid cells, unchanged count from today):
1. Date (unchanged)
2. Amount — relabeled "Amount", unsigned placeholder `"25000"`
3. Currency — **new cell**, placed immediately after Amount (same visual pairing as "amount + currency" in REC-04's literal wording); text input, default `"IDR"`, width matches other grid cells (not a half-width inline pairing — full grid cell, simplest diff per Pitfall-avoidance in RESEARCH.md)
4. Category (unchanged, still cell position after Currency)
5. Merchant / note (unchanged)
6. Account (unchanged single select)
7. Notes (unchanged)
   - The old `is_transfer` checkbox cell (grid position 8) is **deleted entirely** — the grid shrinks from 8 cells to 7, ending on an odd cell count, which is fine since CSS grid auto-wraps.

**Transfer** (6 grid cells):
1. Date (unchanged)
2. Amount — unsigned, same label/placeholder as Expense/Income
3. Currency — same new cell as above
4. From account (replaces Category cell position — a `<select>` sourced from the same `accounts` prop)
5. To account (replaces Merchant/note cell position — a `<select>` sourced from the same `accounts` prop)
6. Notes (unchanged, maps to `TransferCreate.notes`)
   - No Category cell, no Merchant/note cell (Transfer has no merchant concept — RESEARCH.md's `TransferCreate` has no `merchant` field), no `is_transfer` checkbox.

Grid cell swap is a pure conditional render keyed on `segment`, not a layout reflow — cell count and column count (`1fr 1fr`) stay identical across segments so the modal never visibly resizes/jumps when switching segments.

### 3. Amount + currency field

- Amount input: `type="number"`, `step="any"`, `required`, unsigned. Do not add `min="0"` as a hard HTML constraint (RESEARCH.md notes this is documentation-only, not enforced, to avoid fighting `step="any"` edge cases) — instead rely on `Math.abs()` at submit time (Pattern 2 in RESEARCH.md) so a user typing a stray minus sign is silently corrected rather than blocked.
- Placeholder: `"25000"` (was `"-25000"`).
- Label: `"Amount"` (was `"Amount (negative = expense)"`) — this exact label text is the retirement of the sign-convention foot-gun (D-02).
- Currency input: plain `<input type="text">` using the `input` token, not a `<select>` (per RESEARCH.md Anti-Pattern: no hardcoded currency enum since neither `TransactionCreate.currency` nor `TransferCreate.currency` validates against an enum server-side). Default value `"IDR"`. Label `"Currency"`.

### 4. "Save & add another" (D-06)

- Second `<button type="submit">` in the button row, positioned **between** the primary Save/Add button and the error message span (order: Cancel → primary Save/Add → Save & add another → error text).
- Same `btn` token styling as the primary button (both are green/accent-weight — CONTEXT.md does not call for a visual hierarchy between the two Save actions; they are equally valid "commit" actions, just with different post-submit behavior).
- **Create-mode only** (`!isEdit`) — not rendered when editing an existing record (RESEARCH.md discretion recommendation, adopted).
- On success: resets `amount`, `categorySelection` (Expense/Income) or leaves From/To unset only if empty before, `notes`/`merchant` to blank/empty string. **Preserves**: `segment`, `accountId` / `fromAccountId` / `toAccountId`, `date`, `currency`. Modal stays open (no `onClose()` call); `onSaved()` still fires so the parent list/summary refreshes in the background.
- Distinguish which button was clicked via a small local state/ref set in each button's `onClick` before the shared `handleSubmit` runs (RESEARCH.md Pattern 7) — do not introduce `e.nativeEvent.submitter` sniffing or a new dependency.

### 5. Account manager (ACCT-01)

No visible change. `AccountManager.tsx`'s table, inline edit row, Add-account form, `ConfirmDialog` reassign flow, and all copy stay byte-identical. The only diff is invisible: `saveAdd`'s POST body gains `type: "liquid"` (D-07). Do not add a type picker, do not touch `saveEdit`'s body (stays `{ name: editName }`) — account `type` is not user-editable this phase (explicitly deferred).

### 6. Platform manager (PLAT-02)

Structural mirror of AccountManager, already correct. One addition: the inline **edit row** gains a second `<input>` for `kind`, positioned exactly where the Add-form's `newKind` input already sits relative to its name input (same `{ ...input, width: 160 }` style, same placeholder `"e.g. brokerage, crypto app"`). Requires:
- New `editKind` state, seeded from `p.kind ?? ""` in the same `onClick` that seeds `editName` (the "Edit" span handler).
- `saveEdit`'s PUT body becomes `{ name: editName, kind: editKind || null }`.
- No other visual change — row layout, table structure, delete/reassign flow, and empty-state copy stay exactly as today.

### 7. Interaction states — edit mode on a transfer leg (Pitfall 1 resolution, adopted per RESEARCH.md recommendation A3-a)

When `TransactionModal` opens in edit mode (`editingTx != null`) and `editingTx.is_transfer === true`:
- Initialize `segment = "transfer"` for **display purposes** but render the segmented control **disabled** (see Component 1 disabled spec) — the user cannot switch away from or re-select Transfer.
- Field layout reverts to the **legacy single Account select** (not From/To) — because this is a single-leg edit of an existing row, not a new pair creation.
- Category cell **is shown** (unlike a fresh Transfer create) since the underlying row may carry a category value from before this phase; do not hide it in this specific edit path — hiding it would silently drop data the row already has.
- Submit path stays `PUT /transactions/{id}` (never routes to `POST /transactions/transfer`) with `is_transfer: true` sent explicitly in the body (hardcoded, since the checkbox UI is removed).
- Show the muted caption below the disabled control: "This is one leg of a transfer — full pair editing isn't available yet." (see Copywriting).
- "Save & add another" is not rendered in this state either (edit mode already excludes it).

This is the smallest-diff resolution preserving today's actual behavior (amount/category/notes/account editable, sign untouched) while preventing the new pair-create endpoint from ever firing during an edit — see RESEARCH.md Pitfall 1 for the failure mode this avoids (silently creating an orphan new pair).
