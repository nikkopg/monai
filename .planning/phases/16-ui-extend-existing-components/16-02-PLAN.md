## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-16-02 | Tampering / Integrity | editing a transfer leg (TransactionModal edit mode) | high | mitigate | Edit-leg lock (Task 3): disabled segment + legacy PUT /api/transactions/{id} with is_transfer:true; the create-only POST /api/transactions/transfer is never called during an edit, preventing an orphan/duplicate pair. Enforced by the record-modal.spec.ts edit-leg-lock scenario. |
| T-16-03 | Tampering | Transfer POST body (TransactionModal Task 2) | medium | mitigate | Body built from an explicit field whitelist (from_account, to_account, amount, currency, date, notes) — never a spread of general form state — so a stray category/is_transfer can't leak into the pair endpoint (RESEARCH Pitfall 2). Asserted by the transfer body-shape scenario. |
| T-16-04 | Spoofing / Tampering | client-derived amount sign | low | accept | Sign derivation is a UX convenience; the backend is the source of truth (Pydantic type validation, TransferCreate.amount gt=0). Single-user self-hosted app — a client that lies about the sign only affects its own ledger. No server change in scope. |
| T-16-05 | Information Disclosure | secrets in client bundle | low | accept | No secret is added to client code; MONAI_API_KEY stays server-side in the /api proxy. Verify no key literal is introduced. |
| T-16-SC | Tampering | npm installs | low | accept | Zero packages installed this plan (pure extension of an existing component). No supply-chain surface. |
</threat_model>
