# Phase 17 — UI Design Contract

> Visual and interaction contract for two NEW surfaces — the Records ledger
> (`ui/app/records/page.tsx`) and Platform detail (`ui/app/investments/[platformId]/page.tsx`).
> The design system below is the project's existing locked system (v1.1
> "paper" aesthetic, reaffirmed in 16-UI-SPEC.md), reused verbatim — no new
> tokens, no new component library. Generated by gsd-ui-researcher, verified
> by gsd-ui-checker.

## Component Contracts (Phase 17 specifics)

### 1. Records page shell (REC-01)

Header row: same layout as Cashflow/Investments (`justifyContent: space-between`, eyebrow+h1 left, nothing on the right except — unlike those two pages — the "+ Add record" `btnDark` button sits in this header row's right side, matching the "Recent transactions" card's `+ Add transaction` button pattern but promoted to the page header since Records has no other card to anchor it to).

Below the header: the filter bar (Component 2), then the date-grouped ledger (Component 3) inside a single `card`-styled container (`{ ...card, marginBottom: 18 }`), matching the "Recent transactions" card shell verbatim.

### 2. Filter bar (REC-02)

Single flex row, `flexWrap: "wrap"`, `gap: tokens.space.sm` (8px), placed as the first child inside the ledger `card`, `marginBottom: tokens.space.md` (14px), background `tokens.color.sidebar` band with `borderRadius: tokens.radius.md`, `padding: 10px 12px` (documented exception: 10px is not a 4px multiple but matches the existing non-4px exceptions already accepted for chrome elements in this codebase — e.g. Phase 16's segmented-control padding: 4 / radius: 9,12 — the alternative, 8px or 12px, was rejected because it visually crowds/loosens the 7-field row; flag for checker as a Spacing exception, same class as Phase 16's).

Field order, left to right: Search (`input`, `flex: 2`, min-width 180) → Account `<select>` (`input`, `flex: 1`) → Category `<select>` (`input`, `flex: 1`, same `flattenCategories()` indent convention as `TransactionModal`) → Type `<select>` (`input`, `flex: 1`) → Min amount (`input type=number`, width 110) → Max amount (`input type=number`, width 110) → Show-transfers checkbox+label (flex-shrink 0, self-aligned center).

Every field change triggers a debounced (300ms) refetch of `GET /api/transactions` with the corresponding query param; `offset` resets to 0 on any filter change (never accumulates stale pages).

**Locked interpretation of `type=transfer` (resolves RESEARCH Open Question 1):** the Type filter's "Transfer" option maps to `transfer_pair_id IS NOT NULL` server-side, NOT the broader `is_transfer=true` flag. Adjustment and Investment-funding rows (`is_transfer=true`, `transfer_pair_id=null`) surface under "Expense"/"Income" by their sign, exactly like any other row — they are never collapsed into a "Transfer: A → B" row (only true `transfer_pair_id` pairs collapse, Component 4). This keeps the Type filter and the pair-collapse logic using the same key, so a row can never appear collapsed under one filter state and single under another.

### 3. Date-grouped ledger + daily net (REC-01)

Client-side grouping over the server-filtered, date-desc flat list (per D-01 — grouping is presentation only). Group key = the row's local calendar date. Each group renders:

- **Group header row**: `display:flex, justifyContent:space-between, padding:"10px 0 6px", borderTop: none for the first group / 1px solid tokens.color.border for subsequent groups`. Left: the day label (see Copywriting). Right: "Net {signed}" — color green if ≥0, terracotta if <0, tabular-nums.
- **Daily net calculation (locked rule, new for this phase):** sum `amount` only over rows where `transfer_pair_id IS NULL` in that day's visible (post-filter) rows. Collapsed transfer-pair rows contribute **zero** to the daily net, whether both legs are visible or only one (the degraded case, Component 4) — a transfer never represents spending or income, so it must never skew the net figure regardless of how many of its legs the current filter happens to show.
- **Row rendering**: each non-transfer row and each collapsed transfer-pair row uses the ledger row shell (Component 4/5) inside the group, `borderTop: 1px solid tokens.color.borderInner` between rows (copied verbatim from the cashflow recent-list).

### 4. Ledger row — normal (expense/income/adjustment/investment-funding)

Copied verbatim from `cashflow/page.tsx`'s recent-transactions row (L742-828), with exactly one addition: a leading 28px checkbox gutter (Component 6) before the existing tint-icon circle. No other change — same icon-chip sizing (38×38, `borderRadius:11`), same primary/meta text stack, same signed+colored amount, same Edit/Delete action links.

### 5. Ledger row — collapsed transfer pair (REC-05, D-07)

Rendered when two rows share a non-null `transfer_pair_id` (Component 3's collapse pass, client-side per D-01/RESEARCH Code Examples).

- Icon chip: `tokens.color.tintNeutral` background, glyph `⇄` (inline text, 15px) in place of the initial-letter avatar.
- Primary text: `"Transfer: {From} → {To}"` where From/To are each leg's resolved account name (looked up from the `accounts` prop by `account_id`, same resolution the modal already does).
- Meta text: `{date}` only — no category (transfers are system-categorized, no category chip shown).
- Amount: unsigned magnitude, `tokens.color.ink`, tabular-nums — no +/− sign (net-neutral, see Color).
- Actions: "Edit" opens `TransactionModal` in the existing transfer-leg-locked mode (`editingTx = legA`, `is_transfer: true` — reuses the Phase 16 `locked` state exactly, no new modal code). "Delete" opens `ConfirmDialog` with the single-transfer-pair-delete copy (Copywriting table); confirming calls the pair-aware delete endpoint for `legA.id` (the backend resolves and removes `legB` per D-04/Pitfall 1-2 — this is a backend contract, not a UI concern, but the UI must send exactly one id and trust the backend to remove both).
- Multi-select: selecting a collapsed row's checkbox marks **both** underlying transaction ids as selected internally (so a bulk-delete request naturally includes both — harmless/idempotent even though the backend would resolve the pair from either id alone).

**Degraded case — sibling not in the current filtered result set** (RESEARCH Assumption A3, e.g. account-scoped filtering shows only one leg): render that single leg as a **normal** ledger row (Component 4 shell, NOT the collapsed "Transfer: A → B" shell — there is no sibling to name), but with a small muted "transfer" tag appended after the primary text (12px, `tokens.color.muted`, in parentheses: "{merchant or account name} (transfer)"). Edit and Delete stay enabled and behave identically to the collapsed row's actions (single-id in, pair-aware resolution happens server-side regardless of what the client currently has fetched). This must never throw — a missing `sibling` is an expected, valid state under filtering, not an error.

### 6. Multi-select + bulk action bar (REC-03)

Checkboxes are **persistent** (always visible, not hover-reveal) in the 28px leading gutter of every row — simplest, no hover-state logic needed, and financial-ledger UIs (the BudgetBakers reference) keep selection affordances persistent too.

When `selectedIds.size > 0`, a bulk-action bar replaces the filter bar's position visually (renders directly below it, `background: tokens.color.sidebar`, `borderRadius: tokens.radius.md`, `padding: "10px 12px"`, `marginBottom: tokens.space.md`, `display:flex, alignItems:center, gap: tokens.space.sm`):

- Left: "{N} selected" (13px/600, ink).
- Right-aligned button group: category `<select>` (inline, `input` token, compact width 160) immediately followed by "Recategorize" (`btn`, green — the one accent target this phase) → then "Delete" (`dangerBtn`, terracotta) → then "Cancel selection" (plain text link, `tokens.color.muted`, clears `selectedIds`).
- "Recategorize" applies immediately on click (no `ConfirmDialog` — matches the existing "category rename is non-destructive, no dialog" precedent from `CategoryManager.tsx`); on success, clears selection and shows the partial-skip note (Copywriting) if any transfer legs were skipped.
- "Delete" opens `ConfirmDialog` with the bulk-delete copy; confirming calls `POST /transactions/bulk-delete` with the full `selectedIds` array (including both legs of any selected transfer pairs, Component 5) and clears selection on success.

### 7. Pagination (REC-01, Discretion resolved)

"Load more" pattern (not numbered pages) — matches RESEARCH's recommendation. Frontend default fetch `limit=100`, `offset` increments by 100 on "Load 100 more" click, appended to the existing list (never replaces it) unless a filter changed (which resets to a fresh fetch at `offset=0`). Backend hard cap stays 500 per request (unchanged, RESEARCH-sanctioned). The "Load 100 more" button is hidden once a fetch returns fewer than `limit` rows (end of results reached).

### 9. Platform detail page shell (PLAT-01, D-08)

Route: `ui/app/investments/[platformId]/page.tsx`. `"use client"`, reads `platformId` via `useParams()`. On mount, fetches `GET /api/platforms/{id}/detail` and `GET /api/portfolio-events?platform_id={id}` in parallel (`Promise.all`, matching the existing `load()` pattern in `investments/page.tsx`).

Header: "← Investments" back-link (12px, muted, `tokens.color.muted2`, `marginBottom: 12`) → eyebrow "Platform" → `<h1>` platform name (40px serif) with the kind tag inline (copied verbatim from the investments group-header markup, L534-550) → 3-stat-card row (Subtotal / Realized / Unrealized, copied verbatim from Cashflow's stat-card grid, `gridTemplateColumns: repeat(auto-fit, minmax(min(100%,200px),1fr))`, `gap:18`).

Below the header: the segmented control (Component 10), then the active tab's table (Component 11 or 12) inside a `card`.

### 10. Segmented control — PnL / Buy & Sell tabs (D-08)

Copied verbatim from Phase 16's Component 1 spec (16-UI-SPEC.md, itself copied from `settings/page.tsx` UIR-07): same container styling (`background: tokens.color.sidebar`, `border: 1px solid tokens.color.border2`, `borderRadius:12`, `padding:4`, `marginBottom:18`), same active/inactive segment styling (ink-on-white active with shadow, muted/transparent inactive). Options: `["pnl", "buysell"] as const`, labels "PnL" / "Buy & Sell". Default active tab on page load: **PnL** (matches the D-08 stated tab order and mirrors "Expense" being first/default in the Phase 16 record-type control).

### 11. PnL tab — holdings table (D-05, Pattern 4)

Column header row copied verbatim from `investments/page.tsx`'s per-holding header (12px, `tokens.color.muted2`, `borderBottom: 1px solid tokens.color.borderInner`, `padding:"8px 0"`): Ticker (flex 1.4) · Qty (flex 1, right) · Avg cost (flex 1.2, right) · Price (flex 1.2, right) · Value (flex 1.2, right) · Realized (flex 1, right) · Unrealized (flex 1, right).

Row styling copied verbatim from the same file's holding-row markup (ticker badge via `badgeColor()`, `fmtQty()` for quantity precision, `pnlColor()` for Realized/Unrealized cell text color). This is a straight filter+redisplay of the same `groups[i]` shape `investments/page.tsx` already renders per-platform — no new visual pattern, just narrowed to one platform and split into explicit Realized/Unrealized columns instead of the main page's combined "Return" column (PLAT-01 explicitly requires both figures visible).

Empty state: same shell as `investments/page.tsx`'s "No holdings in this platform yet." (copy adjusted per Copywriting table — "on" not "in", to read naturally as a page-level empty state rather than a card-level one).

### 12. Buy/Sell history tab — event ledger table (D-05, Pattern 5)
